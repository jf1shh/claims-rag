# Backend critical constraints

* **Vectorized Cosine Similarity**: NEVER calculate cosine similarity using iterative Python loops over individual rows. Chunks must be compiled into a 2D numpy matrix and dot-products calculated in a single matrix multiplication to prevent CPU bottlenecks when scaling.
* **Normalized Embedding Cache Invalidation**: `search_similarity` reads from an in-memory, pre-normalized embedding matrix cache. Any code path that mutates `child_chunks`/`documents` MUST call `self._invalidate_vector_cache()` after commit, or searches will serve stale results. Cache rows are L2-normalized at build time, so the query vector must also be normalized and similarity is a plain dot product — do not reintroduce per-query corpus-norm computation.
* **UTF-8 Robustness**: PDF and TXT text extraction must handle decoding errors gracefully (`errors="ignore"` or similar safeguards) to prevent crashes on non-ASCII symbols.
* **Lazy ML Imports**: `sentence_transformers`/torch are imported inside `EmbeddingEngine`/`RerankingEngine.__init__`, not at module top, so the pure-numpy store stays importable without the ML stack. Keep it that way.
* **Never Synthesize With Zero Retrieved Context**: `AgenticRAGRouter._run_online_agent` must not call the LLM for synthesis when `top_matches` is empty after self-correction — this reliably produces a confident answer that fabricates citations to nonexistent filenames (caught by the eval harness). Any new retrieval-skip path (planner misclassification, new claim scoping logic, etc.) must still be caught by the zero-context hard stop before touching synthesis.
* **Sanitize Every Filesystem-Bound Filename**: any client-supplied filename that touches a filesystem path (upload, delete, download) MUST go through `safe_filename()` (`backend/rag_engine.py`) first. Unsanitized `os.path.join("stored_documents", filename)` is an arbitrary file write/delete vector — this was a real, critical vulnerability, not a hypothetical one. Sanitize once, early, and use the sanitized value consistently for both the DB `filename` column and the physical path, or lookups will mismatch.
* **`engine` Must Stay a Strict Allowlist**: `AgenticRAGRouter.run_query`'s `engine` parameter must only ever resolve to `"simulated"` or the hardcoded local Lemonade URL. Never derive a request URL from client input here — this was a real SSRF + context-exfiltration vector (the full retrieved claim/policy context got POSTed to whatever URL a caller supplied).
* **All SQLite Connections in `SQLiteVectorStore` Must Go Through `self._connect()`**: SQLite ships with `PRAGMA foreign_keys` OFF per-connection, so the schema's `ON DELETE CASCADE` clauses silently never fire on a raw `sqlite3.connect()` — deleting a document orphaned its chunk rows instead of cascading (verified empirically pre-fix). `_connect()` enables the pragma; never add a raw `sqlite3.connect(self.db_path)` inside the store.
* **FTS5 Queries Feeding RRF Must `ORDER BY rank`**: without it, FTS5 returns matches in rowid (insertion) order, so the keyword leg's rank positions in Reciprocal Rank Fusion are arbitrary and `LIMIT` truncates by document age instead of relevance (verified: bm25 order differed completely from returned order on the real corpus).
* **Immutable source publication**: stage a new uniquely keyed source before committing its index/reference transaction. Never overwrite the previous source. Failed publication preserves the prior index and source; delete current bytes after a committed deletion. Reclaim orphan versions with the offline collector. This supersedes the Phase 16 ordering rule; see `docs/portfolio-hardening.md`.
* **Per-Scope Document Identity** (2026-10-20): a document is identified by `(claim_id, filename)`, with `claim_id` NULL for global documents. SQLite indexes `ix_documents_scope ON documents (filename, COALESCE(claim_id,''))` and Postgres has `ix_documents_scope (tenant_id, claim_id, filename) NULLS NOT DISTINCT`; scope matching uses `claim_id IS ?` (SQLite) and `IS NOT DISTINCT FROM` (Postgres). `report.pdf` may exist in claim A, claim B and global scope at once; `add_document` overwrites only the same-scope row. Every lookup, content, download and delete path takes `claim_id`, and a request without it sees only global scope (a claim file then gets 404). `authorize_document` checks claim access BEFORE the lookup so the API is not an existence oracle. Legacy DBs with `filename TEXT UNIQUE` are rebuilt in place by `_init_db` (build `documents_new`, drop, rename; ids kept; `PRAGMA foreign_keys=OFF`). Never reintroduce a filename-only lookup or delete. Drain the async delete queue before deploying a change to the delete message shape: queued messages without `claim_id` read as global deletes. Before 2026-10-20 the table keyed on filename alone and an upload to claim B could silently delete claim A's same-named file.
* **FTS5 Query Tokens Must Be Quoted**: FTS5 operator words (AND/OR/NOT/NEAR) in a bare `MATCH` string are query syntax -- a leading/trailing operator raises a syntax error the `except sqlite3.OperationalError` swallows, silently dropping the whole keyword leg (verified: `MATCH 'OR windshield'` and `MATCH 'glass OR'` both error). Build the keyword query only with `fts_match_query` (`backend/rag_engine.py`), which keeps `[a-z0-9]` runs only and quotes every term, so no query text can reach FTS5 or `websearch_to_tsquery` as syntax.
* **Named-Document Pinning** (2026-10-20): after the cross-encoder ranks the full candidate pool, `pin_named_documents` (`backend/rag_engine.py`, used by the SQLite and Postgres stores) gives up to 2 top_k slots to global reference documents the query names by title: a type word in the title (sop, guideline, guide, rider, endorsement, directive) must appear in the query, along with at least half of the title's distinctive words ("the Subrogation and Liability SOPs" names `SOP_Subrogation_Recovery.pdf` and `SOP_Liability_Determination.pdf`). Only candidates already in the scope-filtered pool are eligible, and claim documents are never pinned, so pinning cannot leak another claim's or tenant's files. Pinned items carry `"pinned": "named_document"` and keep the result order by rank. The naive vector-only mode (`use_fts=False`) is never pinned, so it stays a clean baseline. Why: long claim-scoped audit queries made the cross-encoder rank claim files and case studies above the SOP they cite (rank 6-9 of 15). Prefixing titles to the cross-encoder input was tried and did not help.
* **Claim Rerank Candidates** (2026-10-20): in hybrid search with a reranker and an active claim, `add_claim_candidates` (`backend/rag_engine.py`) adds up to `CLAIM_RERANK_CANDIDATES` (6) of that claim's own parent chunks, best vector score first, to the rerank pool when they are not already in it. SQLite takes them from its full vector ranking; Postgres runs `_claim_ranked`, because its vector leg is `LIMIT`ed to the pool. They are scored like any other candidate and must win on rerank score to reach top_k. Never applied without a claim, in naive mode (`use_fts=False`) or without a reranker, and only the requesting claim's documents qualify. Why: `RERANK_CANDIDATE_POOL` is 15 for latency, and a narrative claim document (`loss_statement_Brooks.pdf` against an SIU checklist query) can fall outside the fused top 15, so the cross-encoder, which ranks it 3rd once it sees it, never scores it. Raising the pool back toward 50 is ruled out (~365 ms vs ~160 ms). Cost on the golden set: a mean of 1.0 extra rerank pair and at most 3.
* **The FTS Keyword Leg ORs Content Terms** (2026-10-21): `fts_match_query` lowercases the query, splits on any non-alphanumeric character, drops one-character tokens and English stopwords/question words, dedupes, caps at `FTS_MAX_TERMS` (32), quotes each term and joins with `OR` (Postgres: `or` for `websearch_to_tsquery`). bm25 (`ORDER BY rank`) / `ts_rank` then ranks by how many and how rare the matched terms are. Both stores must use it, so the two backends stay at parity. Postgres ranks with `ts_rank(..., 1)` (divides by 1 + log(length), like bm25's length term): parity 0.912 -> 0.940 vs the default normalization, `ts_rank_cd` and normalization 8 were worse. ts_rank has no IDF, so the stores still fill unlabelled slots differently (golden top-4 file overlap 0.94 after rerank) while matching on every labelled source; the fake-embedder `parity_runner` exaggerates this because its vector leg is noise. Why: until 2026-10-20 the leg ANDed every purely alphanumeric whitespace token (words with attached punctuation, like "vehicle?" or "claim's", were dropped), so any question with one word absent from a chunk matched nothing: 1 of 33 sourced golden queries had a keyword hit, and "hybrid" was vector plus rerank. Never reintroduce implicit AND for natural-language queries.
* **Answerability Gate Exemptions and Fail-Open** (2026-10-25): `_answerability_gate` must skip any query with a computed `tool_section` and must never refuse when the judge returns None. Why: checklist/triage questions are answered by combining the claim record with SOPs through `claims_tools`, and the judge scored two of the seven such golden questions ~0 (`eval/answerability-probe-2026-10-25.json`); a Lemonade outage must degrade to today's behavior, not refuse every question. The gate is an extra check after the zero-context hard stop, never a replacement for it. Judge prompts must keep "you are not answering the question itself": without it, a passage that answers "no" was scored as not answering.
