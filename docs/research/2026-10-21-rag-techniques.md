# ClaimsRAG retrieval/generation improvement research
Date: 2026-10-21. Read-only research against main at 89ae74e. Measured outcome: see the 2026-10-21 "RAG technique screen" entry in docs/build-history.md (all shortlisted techniques were flat on this corpus, none shipped).

## 1. What ClaimsRAG already does (current baseline)

- **Chunking**: parent/child, char-based (`backend/rag_engine.py` `TextChunker.chunk`, `VectorStore.add_document`): parent `chunk_size=1200, overlap=200`; child `chunk_size=250, overlap=50`. Children embedded (`all-MiniLM-L6-v2`), parents indexed in FTS5. No table-aware/layout-aware extraction — `DocumentParser` appears to be plain text extraction per format.
- **Retrieval**: hybrid — dense (child embeddings, in-memory L2-normalized matrix cache) + FTS5 keyword leg over parent chunks, fused by RRF. FTS5 leg recently fixed (2026-10-21, `fts_match_query`) to OR stopword-filtered quoted terms instead of ANDing (was matching almost nothing — golden hybrid recall 0.929→0.960).
- **Rerank**: cross-encoder `cross-encoder/ms-marco-MiniLM-L-6-v2` (`backend/rag_engine.py` `RerankingEngine`, loaded via `backend/reranker.py`), candidate pool `RERANK_CANDIDATE_POOL=15` (default), with a batching coordinator (`_RerankBatchCoordinator`) that coalesces concurrent rerank calls into fewer model invocations (max_wait_ms/max_requests/max_pairs/inference_batch_size knobs). Remote `RemoteReranker` seam exists (fail-open `FallbackReranker`) but is unused on this GPU-less dev box.
- **Named-document pinning** (2026-10-20): queries that name a document by title get it force-included in top_k (max 2 pins, scope-filtered, not for claim docs, not in naive mode).
- **Claim rerank candidates** (2026-10-20): up to 6 of the active claim's own chunks are added to the 15-item rerank pool if they fell outside it, so the cross-encoder can still see them.
- **Agentic router** (`backend/agentic_router.py`): planner LLM call produces `sub_queries` + `needs_global_policies`/`needs_claim_dossier` flags → per-sub-query retrieval → self-correction if zero context → synthesis; hard refusal if zero grounding. This is a form of query decomposition, not HyDE or multi-query fan-out of the *same* question.
- **Guards**: `answer_guard.py` (withholds unsupported outcome assertions), `conflict_check.py` (LLM-extracted numeric disagreement → `conflicting_evidence`), `prompt_defense.py` (sanitize mode; "sandwich" tested but costs ~0.12 correctness and a reworded sandwich loses protection — don't revisit without new evidence), `provenance_check.py` (redacts attacker-planted identifiers/filenames).
- **Eval**: 34-query golden RAGAS set + adversarial suite (`eval/run_eval.py`, `eval/run_adversarial_eval.py`). Latest (2026-10-21, FTS-OR fix): hybrid+rerank P/R **0.825/0.983**, faithfulness 0.839, correctness 0.840. Judge/generator = Qwen3-Coder-30B-A3B-Instruct GGUF on Lemonade — same model serves both roles, a documented limitation (judge noise band ±0.05–0.13 observed across reruns with *no code change*; never read a single-run delta as a regression).
- **Known-failed/rejected approaches** (`docs/build-history.md`): `RERANK_CANDIDATE_POOL=8` (shipped-then-reverted: looked fine on a quick 18-query golden check, but the full 19-query eval suite caught a real per-query regression — `chen-custom-equipment-cap` correctness 1.0→0.25, `sterling-shop-estimate-detail` 0.75→0.0 — masked by the aggregate barely moving; shipped default is 15). Lesson recorded: *never trust a partial/quick eval for a retrieval-affecting config change — always run the full suite.* "Prompt-defense sandwich" reworded to avoid the "answer only" instruction recovered quality but lost all held-out adversarial protection — the narrowing *is* the protection; don't re-loosen it. HNSW index deliberately unused on the Postgres leg (exact scan preferred for parity proof) — a Phase-6 optimization once parity is locked, not a quality item.

## 2. Technique-by-technique evaluation

### A. Better small local embedding model (bge-small-en-v1.5 / bge-base, gte-small, nomic-embed, e5-small, arctic-embed)
- **Evidence**: all-MiniLM-L6-v2 ≈ 42 BEIR NDCG@10 average; bge-small-en-v1.5 ≈ 52–54 BEIR NDCG@10 — roughly +10 points, same 384-dim output, comparable CPU latency, both well under 5ms/sentence on CPU-class hardware. [BAAI/bge-small-en-v1.5 (HF)](https://huggingface.co/BAAI/bge-small-en-v1.5), [Embedding Model Benchmarks: Speed vs Quality for RAG Retrieval](https://www.generalcompute.com/blog/embedding-model-benchmarks-speed-vs-quality-for-rag-retrieval), [RuVector issue #524 measured +0.08 nDCG@10 on BEIR NFCorpus bundling BGE alongside MiniLM](https://github.com/ruvnet/RuVector/issues/524).
- **CPU/local feasibility**: trivial — same `sentence-transformers` API, same dimensionality (no VectorStore schema change if staying at 384-dim; bge-base is 768-dim and would need a re-embed + schema/column size check). Model is ~130MB, loads in the same lazy-import path as MiniLM.
- **Already done?** No — `all-MiniLM-L6-v2` is a *Locked Design Decision* in `docs/architecture.md` ("Lightweight, runs extremely fast on CPU, high similarity accuracy" — that reasoning is now dated; no comparative number is cited in the lock).
- **Benefit here**: likely real precision/recall gain on the dense leg specifically (today's 0.825/0.983 hybrid numbers are dominated by rerank + FTS fixes, not embedding quality — dense leg has had the least recent attention). bge-small also supports instruction prefixes (`"Represent this sentence for searching relevant passages:"`) which can help short claims-handler queries match longer SOP prose.
- **Risk**: requires a full re-ingest (all 48 docs) and re-embed — not free, and it's a corpus-wide change that invalidates any embedding-level caching; must re-run full golden+adversarial suite per the pool=8 lesson, not just a quick check. Swapping the locked decision needs sign-off since it's explicitly recorded as locked.
- **Implementation sketch**: `backend/rag_engine.py::EmbeddingEngine` model name (config-driven, probably already a parameter) → change to `BAAI/bge-small-en-v1.5`; add query-side instruction prefix in the query-embedding call path (`agentic_router.py`/`rag_engine.py` wherever `encode()` is called for queries vs documents — bge needs asymmetric prefixing, document side gets no prefix); re-run `ingest_all.py`; full `eval/run_eval.py` + `eval/run_adversarial_eval.py`; update `docs/architecture.md` Locked Design Decisions table with the new number and reasoning before merge.

### B. Better reranker (bge-reranker-v2-m3 vs current ms-marco-MiniLM-L-6-v2)
- **Evidence**: bge-reranker-v2-m3 (568M) MTEB NDCG@10 ≈ 0.5526 vs ms-marco-MiniLM-L6-v2 ≈ 0.5082 — a real quality edge — but on CPU ms-marco-MiniLM-L6-v2 does ~143.9 pairs/sec vs bge-reranker-v2-m3's ~6 pairs/sec (~24x slower), i.e. ~130ms per 16-pair batch for bge-v2-m3. [Reranking Models Compared: NDCG, Latency, Cost](https://gigarag.com/blog/reranking-models-compared), [arXiv 2409.07691 Benchmarking rerankers](https://arxiv.org/pdf/2409.07691).
- **Already done?** Rerank pool is already tuned (15, after the pool=8 regression) and there's a micro-batching coordinator specifically built to amortize rerank cost — the system is latency-sensitive at this exact point.
- **Benefit here**: marginal-to-unclear. ClaimsRAG's own debugging history shows retrieval-recall problems (pool size, FTS AND-bug, missing claim docs) dominated the loss, not reranker-model quality; a slower, "better" reranker on CPU directly fights the just-landed batching/latency work (session 578 in build-history: pool was tuned specifically because a GPU reranker wasn't available on this box).
- **Risk**: ~24x per-pair cost increase at pool=15 (15 pairs × batching) could push rerank latency from ~155–167ms back toward multi-second territory on CPU — a regression of exactly the kind the maintainer already fixed once. 568M model RAM footprint is also much larger than the 22M-param MiniLM cross-encoder.
- **Verdict**: not worth it as a wholesale swap. If reranker quality is revisited, do it only behind the existing `RemoteReranker`/GPU seam (already designed for exactly this), not as the CPU-path default.

### C. Contextual retrieval / contextual chunk headers (Anthropic, Sept 2024)
- **Evidence**: Anthropic's own numbers: Contextual Embeddings alone cut top-20 retrieval failure rate 5.7%→3.7% (−35%); + Contextual BM25 → 2.9% (−49%); + reranking → 1.9% (−67%). [Anthropic: Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval). Independent reproductions report 5–15% precision gains across datasets, and a codebase-retrieval eval saw Pass@10 ~87%→~95%. [Contextual Retrieval in 80 Lines (measured)](https://dev.to/gabrielanhaia/contextual-retrieval-in-80-lines-anthropics-chunk-prefix-trick-measured-on-your-docs-3350), [Claude cookbook: contextual embeddings guide](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide).
- **Local/CPU feasibility**: the context-generation step needs an LLM call *per chunk at ingest time* (Anthropic uses prompt caching against the whole doc to make this cheap on their API). Locally this means one local-LLM call per parent chunk during ingestion — for ~48 docs × several parent chunks each, that's a few hundred extra LLM calls, one-time, at ingest (not query time), using the same Lemonade/Qwen3-Coder endpoint already in the stack. This is exactly the kind of cost ClaimsRAG already pays elsewhere (planner, conflict_check, provenance_check all make per-answer LLM calls); an ingest-time cost is cheaper to amortize than a query-time one.
- **Already done?** No — current chunk headers/metadata are plain filename/claim scoping, not an LLM-generated "this chunk is from doc X, discussing Y, in the context of Z" prefix.
- **Benefit here**: directly addresses this corpus's actual shape — many short, structurally similar SOP/endorsement/state-code documents where a child chunk ("...the $3,500 cap applies when...") loses which document/coverage/state it's from once separated from its parent. This is plausibly a bigger lever than embedding-model choice for *this* domain, because it attacks exactly the kind of context-loss error already documented in `build-history.md` (the Chen custom-equipment-cap case: retrieval found the right chunk but synthesis under-used it — context-poor chunks are a contributing factor class).
- **Risk**: re-ingest cost (one-time, local LLM), prompt-injection surface if context generation echoes attacker-planted document content into every chunk header (would need to run through the same sanitization the rest of the pipeline uses); added corpus size (child/parent FTS content grows slightly, embedding dimensionality unchanged).
- **Implementation sketch**: `backend/rag_engine.py::VectorStore.add_document` — after producing `parent_chunks`/`child_chunks`, add a context-generation pass (new function, e.g. `generate_chunk_context(doc_title, full_doc_text, chunk_text, llm_client)`) that prepends a short LLM-generated situating sentence to each child chunk's *embedding input only* (keep stored/displayed content unprefixed, consistent with how FTS and provenance checks currently work on raw content) and optionally to the parent's FTS-indexed text. Wire through `ingest_all.py`.

### D. Query rewriting / HyDE / multi-query expansion
- **Evidence**: HyDE (Gao et al., 2022) outperforms unsupervised dense retrievers on BEIR-style zero-shot tasks by generating a hypothetical answer passage and embedding that instead of the raw query, bridging vocabulary mismatch between short queries and longer source prose. [GeeksforGeeks HyDE explainer](https://www.geeksforgeeks.org/data-science/hypothetical-document-embeddings-hyde-hyde/), [Pondhouse Data: HyDE](https://www.pondhouse-data.com/blog/advanced-rag-hypothetical-document-embeddings). General consensus across sources: biggest win is on vague/short queries vs. long technical source docs — plausibly relevant to claims-handler phrasing vs. SOP/endorsement prose.
- **Already done, partially**: the agentic router's planner already decomposes a query into `sub_queries` — a form of query transformation — but does not generate a hypothetical *answer passage* for embedding.
- **Benefit here**: unclear/weak evidence of upside *specific to this corpus*, and real downside: HyDE adds a full LLM generation (hallucination surface) in the retrieval hot path, which is exactly the kind of thing `answer_guard`/`conflict_check`/`provenance_check` were built to catch *after* synthesis, not before retrieval. A hallucinated hypothetical document could bias retrieval toward the wrong source, and this corpus already has documented cases of near-duplicate chunks/SOPs where vocabulary bridging could just as easily pull in a *neighboring* wrong SOP (the "audit phrasings retrieve neighbouring SOPs" issue already noted at 2026-10-20, precision 0.528 on the 6 new queries). HyDE could make that specific failure mode worse, not better.
- **Verdict**: not a priority; weak/mixed evidence for this failure mode, meaningful risk, and it duplicates an LLM-cost budget already spent on the planner.

### E. Metadata filtering (state, coverage type, doc type, claim scope)
- **Evidence**: well-established and low-risk pattern (standard RAG engineering practice, not from a single paper) — pre-filter by structured metadata before vector/keyword search to shrink the candidate set to a semantically-plausible subset.
- **Already done?** Partially — claim-scoped vs. global scoping exists, named-document pinning exists. No state-code or coverage-type metadata filter.
- **Benefit here**: plausible real value — state insurance codes and coverage types are exactly the kind of attribute where an SOP for one state getting retrieved for a different-state query is a believable failure mode, and it's currently caught only indirectly (if at all) by text similarity/FTS.
- **Risk**: requires tagging documents at ingest with state/coverage-type metadata (manual or LLM-extracted) and schema changes to `parent_chunks`/`documents` (and the Postgres mirror) — nontrivial for a system with exact SQLite/Postgres parity gates.
- **Implementation sketch**: add `state`/`coverage_type` columns to `documents` (both stores, with an Alembic migration + parity test like the per-scope doc-key migration), a filter clause in the `VectorStore.search_similarity` SQL, and a planner step that extracts `state`/`coverage_type` from the query (reuse the existing planner LLM call rather than adding a new one).

### F. Semantic caching
- **Evidence**: general industry practice (cache embeddings of past queries, serve cached answer on near-duplicate query) — reduces latency/cost, not quality.
- **Already done?** No (only an embedding-matrix cache, not a query/answer cache).
- **Benefit here**: low priority — this is a single-handler, low-QPS internal tool (not a high-traffic consumer product), so cache hit rate is likely low, and claims-handler queries are typically claim-specific (low repeat rate across users). Also risky for a "regulated domain, auditability matters" system: serving a stale cached answer instead of a fresh grounded one works against the provenance/conflict-check design intent.
- **Verdict**: not worth it now; revisit only if the product becomes multi-handler/high-QPS.

### G. RAPTOR / GraphRAG
- **Evidence**: GraphRAG/RAPTOR pay off on multi-hop, cross-entity questions over large, well-connected corpora; they are overkill for small/weakly-connected corpora and single-hop fact lookups, and add real operational cost (graph maintenance, latency, noisy entity resolution). [HackerNoon: When GraphRAG Is Overkill](https://hackernoon.com/when-graphrag-is-overkill-a-break-even-test-for-plain-rag-graphs-and-hybrid-search), [VentureBeat: Stop graphing everything](https://venturebeat.com/orchestration/stop-graphing-everything-when-graphrag-actually-beats-vector-rag).
- **This corpus**: 48 documents, mostly single-claim-scoped lookups and global policy/SOP lookups — the golden eval's hardest cases (Chen custom-equipment, Brooks SIU checklist) are single-document/single-chunk retrieval-depth problems, not multi-hop cross-document reasoning problems.
- **Verdict**: explicitly NOT recommended. Wrong tool for this corpus size and query shape; would add ingestion complexity and a new failure surface for no evidenced benefit here.

### H. Table-aware / layout-aware parsing
- **Evidence**: naive character-chunked PDF parsing missed the right span in 38% of table-grounded questions in a 4,000-filing study; layout-aware chunking (keep tables whole, prepend header row to split fragments) dropped that to 6%. [Towards Data Science: Tables in PDFs for RAG](https://towardsdatascience.com/tables-in-pdfs-for-rag-dont-flatten-the-grid/), [arXiv 2605.00318 Structure-Aware Chunking for Tabular Data](https://arxiv.org/pdf/2605.00318).
- **Already done?** No — `DocumentParser`/`TextChunker` appears to be plain-text, char-offset chunking with no table/layout awareness (confirmed: chunker splits on raw character length, not structure).
- **Benefit here**: this is the single most evidence-backed, domain-matched technique on the list. ClaimsRAG's documents explicitly include deductible tables, plan-letter/coverage tables (`claim_tools.py`-style structured data used by `agentic_router.py`'s `deductible_apply`/`plan_letter`/`coverage_of`), state-code tables, and dollar-amount line items — exactly the content type where naive char-chunking is documented to fail (the Chen custom-equipment-cap bug — missing/undercounting line items in a receipts file — is a plausible instance of this exact failure class, and it was fixed by a prompt change, not a parsing fix, so the underlying chunking weakness may still be latent for other documents).
- **Risk**: parsing-layer rewrite touches `DocumentParser` for every format (PDF/DOCX/XLSX/TXT) ingestion must stay correct for; moderate ingestion-time cost increase; must preserve the 100%-local constraint (no cloud document-intelligence APIs — local tools like `camelot`/`pdfplumber` table extraction, or a local vision-table model, would be needed, not Azure Document Intelligence or similar).
- **Implementation sketch**: `backend/rag_engine.py::DocumentParser` — add table detection (e.g. `pdfplumber`'s `extract_tables()`, already CPU-local) and emit table content as Markdown with header row preserved, keeping each table as its own parent chunk (don't let `TextChunker.chunk`'s char-window split a table mid-row). Add a golden-eval query targeting a known table (deductible table, state-code table) if one doesn't exist, to make this measurable.

### I. ColBERT / late interaction, late chunking
- **Evidence**: late-interaction retrieval (ColBERT) and late chunking (embed the full document, then pool into chunk-level vectors) both aim to preserve document-level context lost by independent chunk embedding — overlapping goal with contextual retrieval (D above), generally compared head-to-head with it. [Particula: Contextual Retrieval vs Late Chunking](https://particula.tech/blog/contextual-retrieval-vs-late-chunking).
- **Local/CPU feasibility**: ColBERT needs token-level multi-vector storage (much larger index, specialized scoring) — a bigger architecture change than this system's SQLite/pgvector single-vector-per-chunk design supports without a major rework; late chunking needs a long-context embedding model (MiniLM's context window is short, ~256 tokens, so late chunking isn't meaningfully usable with the current embedding model without also swapping it).
- **Verdict**: not recommended now — higher engineering cost than contextual retrieval (C) for a similar or smaller documented benefit in this evidence set, and conflicts with the locked SQLite/pgvector single-vector schema that the Postgres parity work (Phase 17) was just built and verified around.

### J. Self-RAG / corrective RAG as a new mechanism
- **Already done**: the agentic router's "self-correction if zero context" step and the answer guard/conflict check/provenance check pipeline already implement most of corrective-RAG's intent (detect bad grounding, withhold or correct) — adding a separate "Self-RAG" framework would be redundant with code already in place and verified by the adversarial suite.
- **Verdict**: no action — already covered by existing, evaluated mechanisms.

### K. Citation/attribution techniques
- **Already done**: `provenance_check.py` already traces identifiers/filenames back to source sentences; answers already cite source filenames (router prompt: "Cite source filenames in your explanation"). Evidence-based additions (e.g., sentence-level citation spans) exist in the literature but there's no documented gap here — current citation granularity (filename-level) is adequate for the domain (claims handlers need "which document," not necessarily "which sentence").
- **Verdict**: low priority; no identified gap.

## 3. Ranked shortlist — what's worth doing now

1. **Table-aware/layout-aware parsing (H)** — strongest domain-matched evidence (38%→6% failure rate on table-grounded questions in the cited study), directly targets this corpus's deductible/coverage/state-code tables and dollar-line-item documents, stays 100% local (pdfplumber-class tools), ingestion-time only cost.
2. **Contextual retrieval / chunk headers (C)** — second-strongest evidence (Anthropic's own measured 35–67% failure-rate reduction depending on combination), directly addresses documented context-loss-shaped bugs in this repo's own debugging history, ingest-time LLM cost only (reuses existing local LLM endpoint), moderate implementation effort.
3. **Metadata filtering by state/coverage-type (E)** — lower evidence weight (general best practice, not benchmark-backed) but low risk and plausible fit for a known failure class (wrong-state SOP collision); defer until after 1–2 land since it needs a schema/migration change on both SQLite and Postgres.
4. **Embedding model upgrade to bge-small-en-v1.5 (A)** — real BEIR evidence (+10 NDCG@10 at equal latency/dim) but lower priority than 1–2 because it requires overturning a *Locked Design Decision* and a full corpus re-embed; also note recent gains (FTS-OR fix, rerank pool, pinning) all came from fixing the retrieval *pipeline*, not the embedding model, suggesting diminishing returns here until pipeline-shaped bugs are exhausted.
5. (Optional, cheap) Add 2–3 new golden-eval queries specifically targeting table/numeric lookups (e.g. a deductible-table or state-code-table question) before implementing #1 — the current 34-query set may already under-represent this failure class, which is why it hasn't been caught yet.

### Explicitly do NOT do, and why
- **RAPTOR / GraphRAG (G)**: wrong tool for a 48-doc, mostly single-hop corpus; adds graph-maintenance and entity-resolution failure surface with no evidenced benefit here.
- **Swap in bge-reranker-v2-m3 (B)**: ~24x slower per pair on CPU for a quality delta that's smaller than the gains already captured by fixing FTS/pool/pinning; directly undoes the latency work the maintainer already did and reverted once (pool=8 lesson generalizes: don't trade retrieval-affecting latency wins away without full-suite proof the trade is worth it).
- **HyDE / hypothetical-document query expansion (D)**: weak evidence of benefit specific to this corpus's failure mode, real risk of amplifying the already-documented "audit phrasings retrieve neighbouring SOPs" cross-contamination problem, and duplicates LLM budget already spent on the planner.
- **Semantic caching (F)**: low query volume / low repeat-rate use case, and caching stale answers cuts against the auditability goals of the guard/conflict-check/provenance stack.
- **ColBERT / late chunking (I)**: bigger schema rework than contextual retrieval for overlapping benefit; conflicts with the just-verified SQLite/pgvector single-vector parity design.
- **Self-RAG as a new framework (J), new citation machinery (K)**: already implemented in spirit by existing guard/conflict/provenance checks; no identified gap to justify new code.
- **Any change to `RERANK_CANDIDATE_POOL` without the full eval suite**: already a documented lesson (pool=8 regression) — repeat it for any future pool/model tuning, not just a golden-query spot check.

## 4. Eval plan for whichever of #1–#3 gets implemented

Use the repo's existing harness exactly as the `pool=8` lesson prescribes — never ship on a partial signal:
1. Baseline: capture current numbers before changing anything — `eval/results-2026-10-21-34row-fts-or.json` hybrid P/R 0.825/0.983, faithfulness 0.839, correctness 0.840 is the latest baseline to diff against.
2. Implement one technique at a time (not combined), on its own branch.
3. After each: run `.venv/bin/python -m pytest tests/ -q` (regression-free) and `scripts/run_foundation_gates.py --mode gate` (0 blocking).
4. Run the **full** 34-row golden suite (`eval/run_eval.py`) twice (per the documented judge-noise practice — single runs are not trustworthy) and compare per-query, not just aggregate (the pool=8 lesson: aggregate hid two real per-query regressions).
5. Run `eval/run_adversarial_eval.py` against the known/held-out/conflict baselines (25%/58%/11-11 pattern) — a parsing or chunk-header change that injects LLM-generated or table-extracted text into chunks is new prompt-injection surface and must be checked by the adversarial suite, not just the golden suite.
6. For table-aware parsing specifically: add 2–3 new golden queries that target table content before/after, since the existing 34 may not isolate this failure mode (recommendation #5 above).
7. Record result, including any reverted attempt, in `docs/build-history.md` Debugging History exactly as the pool=8 and sandwich-prompt entries are recorded — win or lose.
8. Update `docs/architecture.md` Locked Design Decisions only if a change ships as the new default (e.g., embedding model swap), with the new benchmark numbers as the reasoning, replacing the now-dated "fast on CPU" justification.
